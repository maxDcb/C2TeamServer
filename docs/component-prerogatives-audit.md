# Audit des prérogatives des composants — première passe, 25 octobre 2026

Cet audit examine **qui décide, qui détient l'état et qui exécute** dans les versions actuellement épinglées par les trois parents. Il complète les [inventaires](inventory-index.md), le [suivi des transports](audit-status-2026-10-25.md), la [revue GUI ↔ serveur des listeners](listener-ui-server-audit.md) et celle des [sessions](session-ui-server-audit.md). Une capacité observée dans le code n'est pas une approbation de son périmètre. Cette première passe est statique : les scénarios de fonctionnement et la validation de la release restent à faire.

## Constats à traiter en priorité

1. **Autorisation des opérateurs.** Les RPC autres que `Authenticate` appellent `ensureAuthenticated`, mais [TeamServerAuth](../teamServer/teamServer/TeamServerAuth.cpp) valide uniquement la présence et l'expiration d'un jeton. Le fichier d'identifiants contient des noms d'utilisateur et des hashes, sans rôle ; le jeton n'est pas associé à l'utilisateur dans l'état actif. Le code inspecté ne distingue donc pas les prérogatives « voir », « commander », « gérer les identifiants » et « administrer les listeners ». Les RPC typés donnent accès à l’hébergement d’artefacts et au rechargement des modules via [TeamServerLocalOperationService](../teamServer/teamServer/TeamServerLocalOperationService.cpp), ainsi qu’au coffre via son service dédié. Décider si un rôle unique est voulu ; sinon, définir la matrice de droits côté serveur et conserver l'identité de l'opérateur avec le jeton.
2. **Exécution locale du client.** [TerminalPanel](../C2Client/C2Client/TerminalPanel.py) clone les URL des fichiers `.conf`, ajoute leurs répertoires à `sys.path` et importe les modules ; [ScriptPanel](../C2Client/C2Client/ScriptPanel.py) importe les scripts du dossier local. Cette exécution se produit dans le processus client et dépasse sa fonction de présentation. Auditer l'origine, la version fixée, les droits du processus et les déclencheurs avant de considérer ces extensions comme fiables.
3. **Identité et état après redémarrage.** Les listeners et sessions sont tenus en mémoire dans le [service](../teamServer/teamServer/TeamServer.hpp) et le [cœur](../core/listener/Listener.hpp), tandis que les jobs disposent d'une persistance SQLite. Le client doit rafraîchir l'état après reconnexion et les commandes doivent résoudre la route actuelle. La campagne précédente a corrigé des cas de routage ; il manque une preuve de bout en bout après redémarrage serveur avec listener recréé et commande en cours, comme indiqué dans le [suivi](audit-status-2026-10-25.md).
4. **Privilèges d'installation et artefacts.** [L'installateur](../packaging/exploration_install.py) peut écrire les secrets/configurations et démarrer les processus. Le workflow de release importe actuellement les deux releases d'implants sans prouver leur commit source dans le paquet final. Une installation testée doit être liée aux commits des trois parents, aux deux archives d'implants et à leurs empreintes ; voir le [gate](submodule-release-policy.md).
